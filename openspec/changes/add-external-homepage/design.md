## Context

The blog is generated by Gatsby 5. Until now, the site root `/` was a Gatsby-generated page (the paginated article list, via `gatsby-awesome-pagination` in `gatsby-node.js`). The author now wants a separate, framework-free landing page (HTML + CSS + browser-side JSX-via-Babel-Standalone) to live at `/`. The landing page lives in its own private repo (`memset0/memset0.github.io`) so it can be edited independently of the blog.

This change leaves the surrounding site (categories, doc-mode, friends, comments, search, frontmatter contract) untouched.

## Goals / Non-Goals

**Goals:**

- The site root `/` serves a single artifact owned by the external repo — no Gatsby framework code, no MUI, no client-side hydration shell.
- The article list moves to `/posts/` and behaves exactly as the old `/` did (same pagination, same sort, same filtering).
- A developer running `npm run dev` or `npm run build` on a fresh checkout gets the homepage repo automatically (no manual clone step in the README).
- CI builds reproducibly from `master` of both repos.
- The two UIs (landing page vs. blog chrome) are intentionally decoupled — the landing page has its own nav; the blog has its own nav; clicking between them is a hard navigation.

**Non-Goals:**

- Reusing the homepage's React-via-Babel approach inside the blog. The blog stays on its compiled Gatsby/MUI stack.
- Building the homepage at build time. The homepage is served as raw HTML/CSS/JSX exactly as it sits in the repo (Babel Standalone in the browser handles JSX at runtime).
- Migrating the old `/about/` content into the new homepage. The old page is kept for deep-link safety but is unlinked from chrome; if the author wants it gone in the future, it's a one-file deletion.
- Server-side redirects (`/` → anything, `/about/` → anything). Static hosting on GitHub Pages doesn't support 301s without `_redirects` workarounds; the author confirmed they're acceptable consequences.

## Decisions

**1. Mount homepage repo at `./homepage/`, use existing static-folders plugin.**

Rationale: The repo is already wired with `gatsby-plugin-static-folders` (it copies `./assets`, `./content/assets`, `./src/images` verbatim into the output root). Adding `./homepage` is one-line and reuses an existing, well-understood path. The plugin preserves relative paths, so `homepage/assets/avatar.png` lands at `/assets/avatar.png` and `homepage/src/app.jsx` lands at `/src/app.jsx` — which is exactly what `homepage/index.html` references via relative URLs.

Alternatives considered: (a) a custom Gatsby source plugin — overkill for static file copying. (b) a custom build script that does `cp -r homepage/* public/` after `gatsby build` — works but bypasses Gatsby's awareness, causing dev-server to miss the files.

**2. Fetch homepage repo via npm `predev` / `prebuild` hook.**

Rationale: This matches how `content/` is treated in CI (checked out before build), but extends the convenience to local dev. The hook shells out to git directly: if `homepage/.git` exists, fast-forward pull; else clone. No `gatsby-source-git`-style plugin is needed; this avoids adding a runtime dependency.

The hook runs every time, so local devs always get the latest from `master`. This matches the author's expectation that the homepage repo IS the homepage — there's no "dev branch" workflow on the gatsby side.

Alternatives considered: (a) `gatsby-source-git` — adds a heavyweight dep and complicates schema; we don't need GraphQL access to homepage files, just static copying. (b) git submodule — breaks the "private content lives separately" pattern, since submodules pin specific commits in this repo.

**3. Move article-list `pathPrefix` from `/` to `/posts/` in `gatsby-node.js`.**

Rationale: The `paginate()` helper in `gatsby-awesome-pagination` generates `/<prefix>/`, `/<prefix>/2/`, etc. Changing `pathPrefix: "/"` to `pathPrefix: "/posts"` (and updating the regex + context fields that downstream templates read) is a 4-line edit that produces the exact target URL shape.

The category-page generation loop (which creates `/oi/`, `/blog/`, etc.) is unaffected — its prefixes were never `/`.

**4. Keep `src/pages/about.js` in place but remove the nav entry.**

Rationale: User said "隐藏" (hide), not "删除" (delete). Hiding from the user-facing nav while leaving the URL functional is the conservative choice; it preserves any inbound deep links that might exist. Future cleanup is one file delete away.

**5. Two independent navs is the intentional end state.**

Rationale: User explicitly chose this — "没有办法的办法" ("the unavoidable solution"). The new homepage is a portfolio surface; bolting the blog nav onto it would defeat the redesign's purpose. We don't inject any back-link or shared chrome.

## Risks / Trade-offs

- **[Path collision between `homepage/` and existing static folders]** → Mitigation: audited before merging. The existing `./assets/` only contains `CNAME`, and homepage doesn't ship a CNAME file. `./src/images/` is a Gatsby-internal path, not duplicated by the homepage. Verified: post-build `public/` has all expected files and no overwrites.
- **[homepage refers to `/src/*.jsx`, which looks like Gatsby source]** → Cosmetic only. There's no actual conflict; Gatsby never serves its own `src/` at runtime. The URL `/src/app.jsx` is unambiguous and resolves to the homepage's JSX file. Future maintainers should know this when grepping for `src/`.
- **[CI fails if PAT can't read `memset0/memset0.github.io`]** → Same PAT already reads `memset0/blog-posts`; both repos are private and owned by the same user. No new credential needed.
- **[Developer without SSH access to the homepage repo can't run dev]** → Acceptable; the same is already true for the content repo. The error message from `git clone` is clear.
- **[`fetch-homepage` script silently overwrites local changes in `./homepage/`]** → It uses `--ff-only` precisely to avoid this. If a developer edits `./homepage/` locally, a non-fast-forward state will error out the pull rather than overwrite — the developer must reconcile manually. Note: the script does not guard against the rare case of a homepage repo without `.git/` (e.g. CI's `actions/checkout` produces this); CI handles its own checkout via the workflow's `checkout` step, so the script's clone-or-pull only runs in local dev.

## Migration Plan

1. Set up local `./homepage/` (a clone of `memset0/memset0.github.io`). Already in place at the time of this change.
2. Apply the file changes (see tasks).
3. Verify local: `npm run clean && npm run build`, then check `public/index.html` is byte-identical to `homepage/index.html`, that `public/posts/index.html` and `public/posts/2/`...`public/posts/N/` exist, that `public/assets/avatar.png` and `public/src/app.jsx` exist, that `public/about/index.html` is still present, and that no other file went missing.
4. Start `npm run dev`; curl `/`, `/posts/`, `/posts/2/`, `/about/`, `/friends/`, `/oi/`, `/assets/avatar.png`, `/src/app.jsx`, `/CNAME` — all should return 200.
5. Commit + push the gatsby-blog repo. CI will then clone both content and homepage repos, build, and push to the deployment repo.

**Rollback**: revert the single commit. No data migration to undo.
