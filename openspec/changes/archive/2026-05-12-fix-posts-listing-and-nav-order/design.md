## Context

Two regressions from `add-external-homepage`, both confined to the gatsby build config and the nav data file. No content/template changes are needed; the underlying page generation and rendering paths are unchanged.

## Goals / Non-Goals

**Goals:**

- `/posts/` and its pagination subpages list the same set of posts the old `/` and `/page/N/` listed (the global `isIndexed=true && isPublished=true` filter).
- The top nav displays entries in the original order with "首页" occupying the previously-final "关于博主" slot.
- The specs are tightened so neither bug can be re-introduced without explicitly contradicting a documented scenario.

**Non-Goals:**

- Adding any new capability or page. This is purely fixing two values.
- Touching `add-external-homepage`'s archived change record. The archive is immutable history; the long-lived specs are where the corrections land.

## Decisions

**1. Tighten the spec rather than only fixing the code.**

Rationale: I made this exact mistake (conflating `pathPrefix` and `prefixRegex`) while reading the spec, and the spec was correct but didn't explicitly call out cross-category aggregation. A future reader (or future me) could fall into the same trap. A clarifying scenario is the cheapest insurance.

For the nav order: "the corresponding chrome slot" is too soft — "last position" is unambiguous and matches the author's intent.

**2. Keep `pathPrefix: "/posts"` and revert only `prefixRegex` to `^/`.**

Rationale: the two values are independent — `pathPrefix` is the URL space for the *generated listing pages* and `prefixRegex` is the slug-space filter for the *posts to include*. The bug was treating them as the same value. The fix is to give each its right value: pages live at `/posts/`, list draws from all slugs (`^/`).

The context-passed `pathPrefix: "/posts/"` should remain `/posts/` because the post-list template uses it to construct in-list `<Link>` hrefs to category sub-prefixes (verified by reading `post-list.js` — it uses `pageContext.pathPrefix` to compute breadcrumbs/links that go to deeper category roots).

**3. Restore the original navigator order exactly.**

Rationale: the simplest fix is to move "首页" from index 0 to the last index, with the other four entries (所有文章, 算法竞赛, 课程笔记, 友情链接) keeping their relative order. This minimizes the diff and makes the regression intent obvious.

## Risks / Trade-offs

- **[Revert reintroduces the original bug from before `add-external-homepage`]** → No: the original code used `pathPrefix: "/"` AND `prefixRegex: "^/"`. The fix uses `pathPrefix: "/posts"` (so listing pages live at the new URL) AND `prefixRegex: "^/"` (so the source filter matches all posts). Both old and new requirements are satisfied.
- **[A site-wide `^/` regex over-matches and includes the new `/posts/` slug itself]** → Posts under `/posts/` don't exist as source markdown (no `content/posts/...` files). The regex matches all *post slugs*, all of which look like `/blog/...`, `/oi/...`, etc. The listing page itself is generated by `paginate()`, not by `allMarkdownRemark`, so there's no recursion.

## Migration Plan

1. Apply the two file edits.
2. `npm run clean && npm run build`. Confirm `public/posts/index.html` is no longer near-empty — it should contain post cards. Pagination should produce `/posts/2/` ... `/posts/N/` for the same N as before `add-external-homepage` (we have ~7 pages from the production content).
3. Inspect `public/posts/index.html` for at least one expected post title (e.g. a recent post known to be `publish: true`).
4. Start `npm run dev`, curl `/posts/` and confirm HTTP 200, body contains post titles.
5. Visually confirm in a browser that the top nav order is 所有文章 / 算法竞赛 / 课程笔记 / 友情链接 / 首页.

**Rollback**: `git revert` the fix commit.

## Open Questions

None — both fixes are deterministic and the spec tightening is straightforward.
